# Git 备份、追回与调试

新手项目里引入 Git，不是为了协作，是为了**吃后悔药**：每到一个能跑的节点就存一个档，改崩了随时能回到上一个好端端的版本。调试则是"给程序看病"的手艺，本文件把它拆成新手照着就能做的动作。

## 一、第 0 步：把 Git 仓库建起来

环境自检通过、项目目录定下来之后，立刻做：

1. **初始化**：在项目目录执行 `git init`；
2. **确认身份**：若 `git config user.name` 为空，先配置 `user.name` 与 `user.email`（只讲这是提交记录上的署名）；
3. **写 `.gitignore`**：把生成物和临时文件挡在仓库外——
   - C/C++：`*.exe`、`*.o`、`*.out`；
   - Python：`__pycache__/`、`*.pyc`、`.venv/`；
   - 通用：`.vscode/`、`.DS_Store`；
4. **首次提交**：`git add .` 后 `git commit -m "第0步 环境自检通过"`。

### 三个区，先讲人话再讲术语

| 区 | 人话比喻 | 对应命令 |
|---|---|---|
| 工作区 | 你正在改的草稿纸 | 直接编辑文件 |
| 暂存区 | 打包封箱的箱子 | `git add` |
| 仓库 | 贴上标签、存进柜子的存档 | `git commit` |

## 二、检查点节奏（与里程碑绑定）

- **每个里程碑验收通过，立刻提交一次**，提交信息固定格式：`第N步 <主题> 验收通过`；
- 大改、重构、试错之前，先确认当前版本已提交——手里有粮，心中不慌；
- 每次提交后，把提交哈希（`git log --oneline` 取前 7 位）和说明记进 `project-state.md` 的检查点表；
- 有远程仓库（GitHub 等）时，一天学习结束可 `git push` 做异地备份；没有远程，定期把整个项目文件夹复制一份到别处，也算备份。

## 三、备份的两个层次

| 层次 | 手段 | 防什么 |
|---|---|---|
| 本地存档 | 频繁 `commit` | 改崩、写错、文件损坏 |
| 异地备份 | `push` 到远程，或复制文件夹 | 硬盘故障、电脑丢失、误删目录 |

提交动作让**用户自己敲**，导师在旁解释每条命令的作用；这是学习目标，不可代劳。

## 四、追回：四种"后悔"场景

先跑 `git status` 看清现状，再对号入座。

| 场景 | 命令 | 后果与注意 |
|---|---|---|
| 改乱了，还没 `add`，想恢复成上次提交 | `git restore <文件>`（旧写法 `git checkout -- <文件>`） | 丢弃该文件未提交的改动，**不可恢复**，先确认没有想留的内容 |
| 已经 `add` 进暂存区，想撤出来 | `git restore --staged <文件>`，再按需 `restore` | 只开箱，不动草稿 |
| 想整体回到某个旧检查点 | `git log --oneline` 找哈希，再 `git reset --hard <哈希>` | 工作区、暂存区全部回到当时；**之后所有未提交改动都会丢** |
| 只想捞回旧版本里的某一个文件 | `git checkout <哈希> -- <文件>` | 只动这一个文件，其他不受影响 |

### 铁律

- `git reset --hard`、`git clean -fd` 这类不可逆操作，**导师必须先说明会丢什么，等用户确认后再执行**；用户拒绝就换方案，不换写法硬来；
- 拿不准时先用 `git stash` 把当前改动收起来，追回后还能 `git stash pop` 找回；
- 每次追回操作后，重新编译运行一次，确认回到的确实是"能跑的那一档"。

## 五、调试三板斧

程序不听话，先别慌，按顺序来：

### 第一斧：读报错

- 从**第一条 error** 读起，后面的报错常是连锁反应，擒贼先擒王；
- 每条报错拆三段：**行号**（哪一行）、**错误类型**（什么病）、**错误信息**（细节）；
- 警告（warning）不是报错，但本技能要求新手阶段**零警告**再往下走。

### 第二斧：打印状态

- 把状态层的数据直接打印出来：坐标、数组内容、分数、条件判断的真假；
- 对照已有定位表：**状态对、画面错 → 渲染层；状态本身就错 → 逻辑层；读进来的键就不对 → 输入层**；
- 打印完记得删，或用注释标记后在收尾时清理。

### 第三斧：最小复现（二分法）

- 新代码一出问题，先注释掉新加的部分，确认旧检查点还能跑；
- 再把新代码**一半一半**地加回来，每加一次跑一次，塌一次就缩一半范围；
- 这与 Git 检查点配合：实在找不到，`git restore` 回到上一检查点，从头再来，胜败兵家常事。

## 六、分层调试对照表

| 层 | 怀疑它时的具体动作 |
|---|---|
| 输入层 | 打印刚读到的按键 / 命令原始值，确认和按的键一致 |
| 状态层 | 打印坐标、数组、长度，对照"应该是多少" |
| 逻辑层 | 打印每个 `if` 条件的真假（0/1），看走的是哪条分支 |
| 渲染层 | 手工改一个状态值，看画面是否跟着变；不变即渲染层问题 |
| 环境层 | 回第 0 步重跑最小程序，排除命令、路径、编码问题 |

## 七、调试纪律

1. **一次只改一处**，改完立刻跑——同时改五处，跑通了也不知道是哪味药起的效；
2. 同一处连续 3 轮修不好，按 [迭代反馈循环](loop.md) 的停滞规则降级或回检查点，不钻牛角尖；
3. 每个修好的 bug，在 `project-state.md` 记一笔"病因 + 药方"，同类坑不踩第二回；
4. 调试是学习主线的一部分，不是额外负担：每经历一次完整的"报错→定位→修复"，在学习看板记一次调试经验。
